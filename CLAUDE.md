## Commands

```bash
npm run dev              # Start dev server at localhost:4321
npm run build             # Build production site to ./dist/
npm run preview           # Build, then run wrangler dev against the build (production-like preview)
npm run check              # astro build && tsc && wrangler deploy --dry-run — validates types and deploy config without publishing
npm run deploy             # wrangler deploy — publish to Cloudflare Workers
npm run cf-typegen         # Regenerate worker-configuration.d.ts from wrangler.json bindings
npm run astro -- <cmd>     # Run any Astro CLI command, e.g. `npm run astro -- check`
npx wrangler tail          # Stream real-time logs from the deployed Worker
```

There is no test suite and no linter configured in this repo. `npm run check` is the closest thing to CI validation (type checking + dry-run deploy).

## Architecture

This is the Cloudflare "astro-blog-starter-template", deployed as a **Cloudflare Worker** (not Cloudflare Pages) via `@astrojs/cloudflare`. Key implications:

- **Adapter output**: `astro.config.mjs` uses the `cloudflare` adapter with `platformProxy` enabled, so `Astro.locals` gets Cloudflare runtime bindings (env vars, KV, etc.) locally during `astro dev` — see `src/env.d.ts`, which types `App.Locals` from `@astrojs/cloudflare`'s `Runtime<Env>`.
- **Worker entry**: `wrangler.json` points `main` at `./dist/_worker.js/index.js` (the adapter-generated worker) and serves static assets from `./dist` via the `ASSETS` binding. `npm run build` must run before `wrangler deploy`/`dev` can find that entry point — this is why `preview` and `check` chain `astro build` first.
- **`worker-configuration.d.ts`** is generated by `cf-typegen` (`wrangler types`) from `wrangler.json` — regenerate it after changing Worker bindings there, don't hand-edit it.

### Content model

- Blog posts are an Astro **content collection** defined in `src/content.config.ts`, loaded via `glob()` from `src/content/blog/**/*.{md,mdx}`. The zod schema there (`title`, `description`, `pubDate`, `updatedDate?`, `heroImage?`) is the source of truth for frontmatter — add fields there first if a post needs new metadata.
- `src/pages/blog/[...slug].astro` uses `getStaticPaths()` over `getCollection('blog')` to statically render one page per post at build time (post `id` = slug), rendering through the `BlogPost` layout.
- `src/pages/blog/index.astro` and `src/pages/rss.xml.js` both independently call `getCollection('blog')` and sort/list posts — there's no shared "get sorted posts" helper, so if post-listing logic changes it currently needs updating in both places (plus the homepage if it also lists posts).
- Site-wide metadata (`SITE_TITLE`, `SITE_DESCRIPTION`) lives in `src/consts.ts` and is consumed by `BaseHead.astro`, `blog/index.astro`, and `rss.xml.js`.
- `astro.config.mjs`'s `site: "https://example.com"` is a placeholder — update it to the real deployed URL, since it's used for canonical URLs, RSS, and the sitemap integration.

### Page shell pattern

Every page assembles the same shell manually: `BaseHead` (in `<head>`, handles global CSS import, meta/OG/Twitter tags, canonical URL) + `Header` + page content + `Footer`. `BlogPost.astro` is a layout wrapping this shell for individual posts (hero image, title, dates via `FormattedDate`); the index/about pages compose the same pieces directly rather than sharing a layout component.
